# E-Market

A multi-shop marketplace built as a reference implementation of
[Flutter Feature-First Clean Architecture (FFCA)](https://engineering.verygood.ventures/architecture/ffca/overview/)
by Very Good Ventures, with a [Serverpod](https://serverpod.dev) backend.

It is a Dart pub workspace with two Flutter apps (admin and customer), feature
packages split into domain, data and presentation layers, shared libraries, and
a Serverpod server whose generated client the data layers consume.

> **Status:** an architecture example, not a finished product. The admin app's
> sign-in, shop selection and Brand management work end to end against the
> server. Other admin pages are placeholders, several data repositories still
> throw `UnimplementedError`, and the customer app is a Flutter scaffold. See
> [What is implemented](#what-is-implemented).

## How the code maps to FFCA

| FFCA concept | Here |
| --- | --- |
| **Apps** compose features and shared libraries, and own routing, environments and providers | `apps/admin`, `apps/customer` |
| **Features** are a small set of packages, one per layer | `features/<feature>/<feature>_{domain,data,*_presentation}` |
| **Domain layer** (pure Dart): models, business rules, repository interfaces | `catalog_domain`: `Brand`, `BrandInput.create`, `IAdminBrandRepo` |
| **Data layer**: implements repository interfaces, owns clients and DTO mapping | `catalog_data`: `AdminBrandRepoImpl` over the Serverpod client, AutoMappr DTO mappers |
| **Presentation layer**: widgets and the blocs that tie the domain to them | `catalog_admin_presentation`: `BrandListBloc`, `BrandFormBloc`, `BrandListModule` |
| **Shared libraries** carry no feature knowledge | `shared/*`: UI kits, bootstrap, logging, local storage, data and presentation utilities |

Dependencies point inward. Data and presentation depend on domain, domain
depends on neither, features depend only on shared libraries, and only apps
wire concrete data implementations to domain interfaces.

```text
apps/admin ──> features/*/{domain,data,admin_presentation} ──> shared/*
apps/customer ──> features/*/{domain,data,customer_presentation} ──> shared/*
features/*/*_data ──> backend/emarket_client (generated by emarket_server)
```

Two apps share one backend, so a feature can have one presentation package per
app (`catalog_admin_presentation`, `catalog_customer_presentation`) and admin
and customer repository interfaces (`IAdminBrandRepo`, `ICustomerBrandRepo`)
backed by separate Serverpod endpoints.

**Start reading at the Brand slice.** It is the most complete feature and the
template for the Mason feature brick:

1. `backend/emarket_server/lib/src/brand/`: model (`brand_dto.spy.yaml`) and
   admin and customer endpoints
2. `features/catalog/catalog_domain/`: `Brand`, `BrandInput`, repository interfaces
3. `features/catalog/catalog_data/`: repository implementation and mapper
4. `features/catalog/catalog_admin_presentation/lib/brand/`: blocs and modules
5. `apps/admin/lib/modules/brand/brand_list_page.dart`: the route that composes them
6. `apps/admin/lib/app/app_providers.dart`: where the repository is bound to its interface

Design decisions and their reasons are in [`docs/architecture/`](docs/architecture/).

## Repository structure

```text
emarket/
├── apps/
│   ├── admin/                 # Admin app: composition root, routing, pages
│   └── customer/              # Customer app (scaffold)
├── features/                  # auth, catalog, customer, media, shop, staff
│   └── catalog/
│       ├── catalog_domain/
│       ├── catalog_data/
│       ├── catalog_admin_presentation/
│       └── catalog_customer_presentation/
├── shared/                    # Libraries with no feature knowledge
├── backend/
│   ├── emarket_server/        # Serverpod API, models, migrations
│   └── emarket_client/        # Generated client and protocol models
├── bricks/                    # Mason bricks: feature, package
└── docs/
```

## Set up a fresh clone

### 1. Install prerequisites

Install Flutter 3.47 or newer, Dart 3.13 or newer, Git, and optionally Docker. Then
activate the command-line tools used by this repository:

```sh
dart pub global activate serverpod_cli 4.0.0-rc.2
dart pub global activate mason_cli
dart pub global activate melos 8.6.0
```

The Serverpod CLI version should match the `serverpod` version in
`backend/emarket_server/pubspec.yaml`. The Melos version above matches the
workspace lockfile. Although Melos is activated globally for convenience, the
commands in this README use `dart run melos` so they run the workspace version.

If your shell cannot find `serverpod`, `mason`, or `melos`, add Dart's global
executable directory to your `PATH`:

```sh
export PATH="$PATH:$HOME/.pub-cache/bin"
```

Add that line to `~/.zshrc` or `~/.bashrc` to keep it after restarting the
terminal. Confirm that the tools are available:

```sh
serverpod version
mason --version
melos --version
```

### 2. Install workspace dependencies

From the repository root, resolve the Dart workspace and download the local
Mason brick:

```sh
flutter pub get
mason get
dart pub workspace list
```

### 3. Configure backend passwords

Copy the local development passwords configuration for Serverpod:

```sh
cp backend/emarket_server/config/passwords.yaml.example backend/emarket_server/config/passwords.yaml
```

### 4. Generate source code

Generated Serverpod, Freezed, AutoMappr, and route files are intentionally
not committed. Recreate them after cloning:

```sh
dart run melos run codegen --no-select
```

## Generate a feature

The repository includes a local Mason brick based on the Brand slice in
`features/catalog`. Complete
the fresh-clone setup above before using it.

Generate a feature from the repository root using a lower-snake-case name:

```sh
mason make feature --name category
```

This initializes the domain, data, and presentation packages with
`flutter create --template=package`, applies the Brand-based source templates,
adds the typed feature ID and workspace entries, and runs `flutter pub get`.
The data template expects corresponding Serverpod `<Feature>Dto` and
`EndpointAdmin<Feature>` / `EndpointCustomer<Feature>` client types. The hook attempts `build_runner` in all three
feature packages; individual generation failures are reported without stopping
the remaining packages or failing feature creation.


## Run the project

### 1. Start Serverpod Backend & Services

Serverpod v4 features an embedded PostgreSQL database (with `pgvector` & `postgis`), meaning **Docker is completely optional** for local development.

#### Option A: Zero-Docker Full Stack (Recommended)
From the workspace root, start Serverpod v4 with its interactive Terminal UI, hot reload, embedded PostgreSQL, and automatic migrations:
```sh
# Start Serverpod v4 full stack (TUI + embedded DB + hot reload)
dart run melos run server:stack

# Or start the embedded database standalone over TCP:
dart run melos run server:db:start

# Run pending database migrations only (maintenance mode):
dart run melos run server:migrate
```

#### Option B: Docker Containers (Alternative)
If you prefer running PostgreSQL and Redis via Docker containers:
```sh
# Start Docker containers (Postgres & Redis) and start Serverpod:
dart run melos run server:dev

# Manage Docker containers only:
dart run melos run server:docker:up
dart run melos run server:docker:down
```

Alternatively, you can manually navigate to `backend/emarket_server`:

```sh
cd backend/emarket_server

# Copy local passwords template if passwords.yaml does not exist
cp config/passwords.yaml.example config/passwords.yaml

# Run the Serverpod v4 unified start command
serverpod start
```

To create a development admin without exposing registration in the admin app,
set both seed variables when starting Serverpod:

```sh
DEFAULT_ADMIN_EMAIL=admin@emarket.local \
DEFAULT_ADMIN_PASSWORD='choose-a-local-password' \
dart run bin/main.dart --apply-migrations
```

The seed runs only in Serverpod's `development` mode. It is idempotent: a
missing account is created, while an existing account keeps its password. Do
not commit a real password or use this seed as a production provisioning
mechanism.

### 2. Run the Flutter applications

Run either Flutter application from the repository root:

```sh
# Admin app (use a server address reachable from your device or emulator)
(cd apps/admin && flutter run -t lib/main_dev.dart --dart-define=SERVER_URL=http://localhost:8080/)

# Customer app (scaffold only)
(cd apps/customer && flutter run)
```

The server's `flutter_build` script builds the customer web application into `backend/emarket_server/web/app`.

